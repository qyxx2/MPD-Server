## 根因与关键执行时序

1. 正常绑定覆盖 MPD 中的业务 current + Pending；Played 只在业务 Queue 的负 position 区域。binding 保留 occurrence、MPD Song ID、URI、位置，带 service/connection epoch、partition、playlist version、binding generation；preflight 使用完整业务 baseline 核对真实 MPD。
2. 原 `_prepare_play(song)` 仅生成 `prepare:<MPD ID>` 临时身份。选择已有相同 URI，或 add 新条目再 play；执行器逐命令保存 sent/ACK/confirmed 和完整 sample。
3. 重播不在 MPD 中的 Played 会增加 playlist version，play 改变 actual current。原 Pending 的 MPD ID 实际仍在，且没有被修改。
4. 业务 `play_now` 把目标 Played occurrence 设为 current，旧 current 转为最近 Played，Pending 的 occurrence 与相对顺序不变。
5. 原 sync 新鲜读到 prepare 的结果，但仍调用旧 binding 的 `accepts()`。版本/完整队列不同使其拒绝并清掉 `binding/synced_entries/sync_sample`；所有 Pending 变为“没有已知 ID”。sync 重新 add 全部目标、再次 play、删除全部旧执行条目。严格的逐命令全量确认使样本读取随命令数增长，完整队列内容又随 N 增长。

修正后的局部移交：

- `play_now(queue_item_id)`、`previous`、共享 occurrence 选择路径 `next` 显式传入目标 occurrence。`_prepare_play` 核对其业务 Song 身份；已有 binding 必须接受准备前的完整 baseline，才把该 binding 的映射放入固定 prepare intent。
- 目标已在映射中则使用该 occurrence 的 MPD ID；目标是 Played 则以该 occurrence 为 add identity，即使 Pending 有相同 URI也新增该 Played 执行项。重复 URI 分支必须使用既有 `queue_play(ID)`，唯一 URI 仍沿用原 transport；两者执行确认都检查预定 ID。未实施 Batch 5 的全局直接 playid 优化。
- sync 通过同一 allocation/attempt owner 的 `execution_preparations` 找到固定 prepare intent，并要求其目标 ID 精确等于新的业务 current occurrence。移交前验证最终 sample 存在、所有命令 confirmed、无 UNKNOWN、原执行 fences，以及新鲜完整 sample 与最终确认的 connection/partition/version/全部 entries/current/state/modes 一致。
- 验证通过后才暂时退役旧 binding，将该 intent 的 occurrence 映射和 confirmed sample 交给现有 sync planner。不提前增加 binding generation；现有 `preserve_binding`/外层 rollback 恢复业务侧绑定，外部副作用继续保留在 receipt 前缀中。
- planner 只移动已确认的 Played 新 current 到前面、删除已离开的旧 current。Pending ID 不变；current 已确认播放时不再 play/seek，不重置进度。最终完整 Queue 确认后才建立新 binding、提交业务/History/receipt/实时通知。
