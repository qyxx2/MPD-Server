# 第三章：系统架构与播放输出设计

## 1. 设计状态与范围

- 设计类型：Architectural（架构设计）。
- 本章状态：用户已确认对话中的设计，可进入书面规格审阅。
- 首期输出：NAS 本机 USB DAC，沿用现有 MPD → ALSA → USB DAC 链路。
- 第二阶段输出：客户端 HTTP 音频串流。首期定义接口与状态模型，但不实现串流服务或客户端音频播放。
- MPD 信息页：参照 myMPD「关于」页面的简洁方式，只展示 MPD 本身能够提供的信息。
- 首期不建设 NAS CPU、内存、负载、磁盘和网络吞吐等系统监控仪表盘。

## 2. 架构方案与职责边界

### 2.1 方案比较

| 方案 | 结构 | 特点 |
|---|---|---|
| A：Music Server 统一控制 | 客户端 → Music Server → MPD | Queue、播放规则、歌单和输出模式由 Music Server 统一管理 |
| B：客户端直接控制 MPD | 客户端 → MPD | 路径较短，但业务规则可能分散在多个客户端 |
| C：混合控制 | 客户端同时调用 Music Server 和 MPD | 灵活，但容易产生状态同步和控制权冲突 |

**采用方案 A。** 客户端不直接承担 MPD 的业务控制逻辑。Music Server 是播放控制的统一入口，MPD 负责实际音频播放。

### 2.2 核心原则

1. 播放控制与音频输出分离：播放规则由 Music Server 管理，输出设备由 Output Manager 协调。
2. MPD 是首期实际播放引擎，不另建并行播放核心。
3. 客户端展示服务端状态，不自行推断 Queue 或 AutoPlay 状态。
4. 输出模式可扩展：首期实现 USB DAC，第二阶段通过预定义接口增加客户端串流。

## 3. 模块划分

| 模块 | 职责 |
|---|---|
| Playback Service | 处理 Play Now、Play Next、Add to Queue、Pause、Stop、集合播放和输出切换请求 |
| Queue Manager | 管理 Queue 权威状态、歌曲顺序、插队、删除及队列变更 |
| AutoPlay Engine | 按第一章规则补充后续歌曲；尊重用户操作，不静默覆盖 |
| Library Service | 提供歌曲、专辑、歌手、标签、歌词、音频规格和搜索数据 |
| Playlist Service | 管理自定义 Playlist 与 Favorites，并执行歌曲去重规则 |
| History Service | 维护播放历史，包括被切换掉的歌曲 |
| MPD Adapter | 封装 MPD 协议通信、状态读取、输出查询和命令错误处理 |
| Output Manager | 抽象输出模式、协调启停、检查输出可用性并处理切换失败 |
| API / Realtime Gateway | 向客户端提供操作接口、状态快照及实时变化通知 |

首期可将 Output Manager 实现为 Playback Service 内部的独立模块，不要求拆成独立进程。

### 3.1 依赖与数据流

- 客户端通过 API / Realtime Gateway 与 Music Server 通信。
- Playback Service 协调 Queue Manager、AutoPlay Engine、History Service 和 Output Manager。
- MPD Adapter 是 Music Server 与 MPD 通信的封装边界。
- Library Service 和 Playlist Service 提供曲库与播放集合数据。
- MPD 的实际播放状态由 MPD Adapter 读取并映射为服务端统一状态，再同步给客户端。

## 4. 首期音频输出：USB DAC

### 4.1 链路

**Music Server → MPD → ALSA → USB DAC**

首期沿用现有群晖 MPD 和 ALSA 输出路径，不改造音频输出链路。

### 4.2 首期要求

- 查询 MPD 已配置的音频输出，并识别对应 USB DAC 的 ALSA 输出。
- 输出启用、停用等操作只能由 Output Manager 经 MPD Adapter 执行。
- 输出设备不可用、MPD 连接中断或切换命令失败时，向客户端返回明确错误，不得伪报成功。
- 首期不引入客户端音频解码、客户端音量链路或 HTTP 音频传输实现。
- 输出识别不得依赖固定数字 ID；应依据 MPD 查询结果识别输出，并处理输出 ID 变化。

## 5. 第二阶段预留：HTTP 音频串流

### 5.1 目标链路

**Music Server → MPD HTTP 输出 → HTTP 音频流 → 客户端缓冲 / 解码 / 播放**

首期只定义接口与状态模型，不实现串流服务或客户端音频播放。

### 5.2 输出模式与状态模型

输出模式至少包括：

- `NAS_DAC`
- `CLIENT_STREAM`

输出状态至少包括：

- `UNAVAILABLE`：不可用
- `INACTIVE`：未启用
- `PREPARING`：准备中
- `ACTIVE`：活动
- `SWITCH_FAILED`：切换失败

状态对象应预留以下信息：

| 字段 | 含义 |
|---|---|
| `mode` | 当前请求或生效的输出模式 |
| `status` | 输出状态枚举 |
| `targetClientId` | 目标客户端标识；首期可为空 |
| `streamUrl` | 串流地址；首期为空或不支持 |
| `format` | 串流格式；首期未配置 |
| `sampleRate` | 串流采样率；首期未配置 |
| `bitDepth` | 串流位深；首期未配置 |
| `channels` | 声道数；首期未配置 |
| `errorCode` | 可供客户端处理的错误码 |
| `errorMessage` | 面向用户或日志的错误说明 |
| `updatedAt` | 状态更新时间 |

未实现或未知的字段应返回明确的未配置、不支持或空值状态，不得伪造数据。

### 5.3 第二阶段需另行确认的事项

- 固定编码格式与音质限制。
- 流端口与访问地址。
- 鉴权机制。
- 允许的客户端数量。
- 局域网与远程访问范围。
- 客户端缓冲、解码与播放实现。
- MPD 版本和现有配置对 HTTPD 输出的实际支持情况。

不得仅凭源文件位深和采样率宣称客户端串流一定无损或 bit-perfect。

## 6. 输出切换语义

1. 切换输出不等于重新播放一个集合。
2. 默认保留当前歌曲、Queue、播放位置及 Playback Context。
3. Output Manager 先检查目标输出，再执行切换并核对 MPD 实际状态。
4. 切换失败时，若旧输出仍可用则保留旧输出，并向客户端报告失败原因。
5. 首期只有 NAS DAC 可用；客户端串流模式应明确显示为尚未支持，不提供虚假的可用切换操作。
6. 输出切换不得静默清空或重建 Queue，也不得擅自改变 AutoPlay 规则。

### 6.1 v0.1 切换范围与状态事实（2026-10-02 Contract Audit）

本节补齐 Task 7 审计发现的歧义。用户本次明确选择：**只启用目标；实际状态与请求结果分开；HTTP 事务失败后保留实际输出并重新核对**。

- 切换到 `NAS_DAC` 只确保选中的 ALSA 输出启用，不自动关闭其它输出，不引入排他播放模式。显式停用只作用于已识别的 NAS_DAC；它不等于 Playback Stop，不结束 History 会话或改变 AutoPlay。
- 识别使用本次 `outputs()` 返回的特征；不能保存一个固定数字 ID 当成设备身份。多个 ALSA 候选时必须使用注入的 selector，不能猜测；selector 无唯一有效匹配时不可执行控制命令。HTTPD 的存在或启用不使 `CLIENT_STREAM` 在 v0.1 可用。
- 实际输出状态与最近请求状态分开表示。实际 NAS_DAC 状态为 `UNAVAILABLE / INACTIVE / ACTIVE`；请求过程为 `PREPARING`，失败为 `SWITCH_FAILED`，成功时结束准备/失败状态。失败请求不得覆盖仍被实际确认的旧输出状态。
- `ACTIVE` 只表示 MPD 回读确认所选输出已启用，不保证 DAC 物理连接、扬声器出声或 bit-perfect；现有端口不能证明的事实保持未知。无匹配目标、缺少读取能力或无法读取时不得伪报可用。读取可见的 ACTIVE 不等于允许控制；控制能力须另行检查。
- 回读失败时标记当前事实不可确认。可保留最后确认状态供展示，但必须同时标明 stale；不得把缓存 ACTIVE 当成新鲜确认。无历史缓存时也应明确不可确认，不伪造旧输出。
- 所有串流预留信息保持空值；v0.1 的 CLIENT_STREAM 请求返回不支持，不发出 MPD 输出或播放变更命令，不改变当前实际输出。

### 6.2 确认、保留与重试边界

- 每次控制先检查目标及已验证能力，再执行目标布尔启停；不能用 toggle 实现重试。目标已处于所需状态时仍重新核对，不重复发变更命令。
- 成功要求回读确认目标状态，同时确认未改变当前 MPD occurrence、播放状态和执行 Queue；不能仅以命令 ACK 判成功。服务端 Queue（含 revision/顺序/identity）、PlaybackContext、History active/session、AutoPlay 规则保持不变。
- 播放位置按 best-effort 保留：切换不主动 seek、重播或重建 Queue；已暂停的已知位置应保持，播放中的自然时间推进不是位置丢失。未知位置保持未知。发现非自然位置重置或 current/state 漂移时报告 reconciliation failure，不得伪报保留成功或无依据重播旧歌曲。
- 关键输出操作与服务端播放变更采用共同串行化边界。它不能阻止其它 MPD 客户端或 MPD 自然结束；回读发现外部变化时明确报告，恢复由既有 PlaybackService reconciliation 负责，OutputManager 不自行改写播放业务权威。
- 命令失败、超时或取消后不得假定 MPD 未执行。尽可能重新读取输出；无法读取则标记 stale。旧输出仍可用时保留；不得通过关闭其它输出或清空 Queue 实现“恢复”。
- SQLite 回滚不能撤销 MPD 输出变更。若 MPD 已完成而 HTTP 响应序列化、幂等记录或外层事务失败，请求报错、不提交 terminal success，保留并核对实际输出，不自动反向切换。下一次 retry 先回读，再按目标状态执行必要操作。
- 继承已有请求幂等合同：已提交的同请求重放返回原结果且不重复副作用；原结果是请求回执，不充当当前状态读取。未提交成功结果的请求可重试；不同 payload/scope 的同 key 冲突。

### 6.3 输出事件与提交边界

- OutputManager 经既有 `EventPublisher` 发布领域状态变化，不能依赖 WebSocket 实现。
- 成功通知只能在 MPD 确认且所属最外层事务提交之后发布；事务回滚或提交前取消时不得发布该请求的成功通知。PREPARING/失败信息不是成功事件，不能被解释为切换完成。
- 发布器失败不能回滚已经提交的状态或把成功请求改判为失败；必须留下可定位的日志。v0.1 不保证持久化事件投递或 exactly-once，状态读取可以重新确认事实；Task 6 负责后续完整快照恢复，不由 Task 7 实现。
- 若取消发生在 commit 之后，数据库提交事实和幂等回执仍保留；即使响应或事件交付被中断，也不能调用回滚钩子或宣称事务已撤销。
- 输出操作本身不产生歌曲离开、开始或结束的 History 事件。外部实际播放变化仍遵循既有 PlaybackService/History 合同。

## 7. MPD「关于」信息页面

信息页采用简洁呈现方式，参照 myMPD「关于」页面，只展示 MPD 本身实际提供且已验证的字段。

### 7.1 首期建议字段

| 信息类别 | 展示内容 |
|---|---|
| MPD 信息 | MPD 版本、运行时间 |
| 曲库统计 | 歌曲数、专辑数、艺术家数、曲库总时长 |
| 曲库更新时间 | 最近一次更新时间；若正在更新则显示更新状态 |
| 播放统计 | MPD 提供的累计播放时长 |
| 连接状态 | MPD 当前是否连接、是否能够正常读取状态 |

### 7.2 约束

Web 页面布局与通知入口只遵守 [全局 UI 合同](2026-10-03-web-pwa-visual-design.md) WEB-UI-NAV/NOTIFY/BASE：About 和已授权 Output 控制入口归设置，Player 保留 DAC confirmed 摘要；异常/未知/断线原因统一在 app bar 详情。以下“显示异常/更新状态”是语义要求，不授权第二处提示文字。不改变 NAS_DAC/CLIENT_STREAM 支持范围、观察/请求分离或接口。

- 曲库总时长是曲库全部歌曲时长的合计；累计播放时长是 MPD 的播放统计，两者不可混淆。
- 不展示 CPU、内存、负载、磁盘、网络吞吐等 NAS 系统监控指标。
- MPD 未提供或当前版本无法可靠读取的字段，不得猜测补齐。
- 版本及统计字段以当前 MPD 实际返回的数据为准；实现前针对当前使用的 MPD 0.23.5 验证命令与字段。
- MPD 断线时明确显示连接异常，不得将未知数值伪装成 0。

### 7.3 读取与空值边界

- 版本来自注入的已验证 `MPDCapabilities.version`；实时统计及更新状态通过 PlayerPort 读取，不能把 probe 的历史统计样本当作实时值。
- 各字段独立保留未知：未支持、缺字段或当前读取失败的值为 null；MPD 实际返回的 0 则保留为 0。曲库时长 `db_playtime` 与累计播放时长 `playtime` 分别传递。
- 部分读取失败不得丢弃其它成功读取的数据；连接失败、命令拒绝和能力未验证须可区分，不能用统计字段是否非空推断整个 MPD 的连接状态。历史版本信息如保留，必须标识其验证来源，不能证明当前已连接。
- 信息读取无播放、输出或数据库更新副作用；读取更新进度不能触发 `update_database()`。

## 8. 状态同步与错误处理

### 8.1 状态同步

- Music Server 向客户端提供统一状态快照。
- Queue、播放状态和输出状态变化时，向客户端推送更新。
- MPD Adapter 读取 MPD 状态并转换为内部统一格式。
- MPD 暂时断开时，客户端明确显示连接异常。最后一次状态可作为缓存展示，但必须标记为旧数据。
- 客户端重连后重新获取完整状态快照，不能只依赖断线期间的事件。

Task 6 的聚合一致性、外部降级、失效通知/交接和观察生命周期分别以第四章 §12.1–12.3 为唯一协议 authority；History availability 与 playback/progress 权威以第一章 §2.2.1/§8.8 为准。MPD 实际 transport 事实不等于已确认业务会话，发现漂移必须明确表示 reconciliation_required；不能由 API/WS 或只读 observer 擅自改写 Queue/History。第一章要求的自然结束与外部恢复由 PlaybackService 承担，并按 Task 4 专项 corrective 验收后启用，不能用现有方法名称代替该能力证明。

### 8.2 错误处理

| 场景 | 处理方式 |
|---|---|
| MPD 无法连接 | 显示连接异常，暂停依赖 MPD 的操作 |
| USB DAC 不可用 | 显示输出不可用，不伪报播放成功 |
| 输出切换失败 | 返回失败原因；旧输出仍可用时保留旧输出 |
| MPD 返回命令错误 | 转换为客户端可理解的错误信息 |
| MPD 状态与服务端预期不一致 | 重新读取实际状态，以实际状态为依据并同步客户端 |
| 曲库正在更新 | 显示更新中，不误报完成 |

## 9. 首期验收标准

- [ ] 客户端通过 Music Server 控制 MPD，不绕过服务端修改播放业务状态。
- [ ] MPD 能通过现有 ALSA 输出驱动 USB DAC 播放。
- [ ] 播放、暂停、停止、切歌等操作后，客户端状态正确更新。
- [ ] Queue、AutoPlay、History 与第一章确认的规则一致。
- [ ] 「关于」页面只展示 MPD 实际提供且已确认的字段。
- [ ] MPD 连接失败、输出不可用和命令错误能够被识别并反馈。
- [ ] 输出接口及状态模型预留客户端串流模式，但首期不显示虚假的串流可用状态。
- [ ] 输出切换接口的语义不会破坏 Queue、Playback Context 和播放位置。

## 10. 版本兼容与验证说明
