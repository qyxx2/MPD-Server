## 1. 目标和不可退让的合同

目标：在不大规模重构现有 FastAPI/SQLite/MPD/Web 架构的前提下，解决 400 项左右 MPD 执行队列下的普通切歌 2–4 秒等待、Played/previous 的灾难性全队列重建，并明确控制 HTTP 返回后权威 UI 状态收敛问题。

必须保留：

- **MPD 是实际播放/暂停、current 和 elapsed 的权威来源**；MS 编排业务 Queue、Played occurrence、下一首、History、AutoPlay；Web 不通过本地猜测冒充 MPD 状态。
- 真实 MPD 完整 Queue preflight、业务 occurrence↔MPD ID 身份、重复 URI 区分、连接 epoch/partition/playlist version/generation fencing、fixed execution intent、sent/ack/confirmed receipt、UNKNOWN 丢响应不盲重发、rollback/replay、History/Playlist/Queue 事务一致性与提交后可见性。
- 禁止为提速直接删除必要的完整队列校验、按 URI 猜 identity、先删除仍在播放的 current、使用跨事务 TTL availability 缓存，或通过改变网络超时、SQLite PRAGMA、DAC/音频格式宣称性能修复。
- 音乐目录继续只读；实机诊断不能让原 Server 与诊断实例同时控制同一 MPD；必须隔离诊断 DB，记录队列变更和原状态恢复限制。

长期规格：[播放/Queue](../../specs/2026-09-24-playback-model-queue-semantics-design.md) · [总体架构](../../specs/2026-09-25-system-and-development-architecture-design.md) · [Library](../../specs/2026-09-24-library-playlist-tag-search-design-2-1.md) · [Web UI](../../specs/2026-10-03-web-pwa-visual-design.md) · [历史完整 Queue preflight 决议](../plans/2026-10-13-task-9-queue-preflight-safety.md)。保留规格中的原 Task 进度文字只是历史注记，不再授权继续旧路线图。

## 3. 已证实的执行链与瓶颈

### 普通 next / song：重复读取和竞争叠加

- `PlaybackService._verify_user_queue_baseline` 逐个 `get_song`；`next` 的 `_next_available_pending` 遍历全部 Pending；`_desired_song_uris` 再次逐个读取；`play_song_now` 另有可用性遍历。
- `LibraryRepository.get_song` / `_song_from_row` 不只查询一个 URI，而是构建包含歌曲关系与元数据的完整对象。400 项操作出现约 1200 次读取和近 9000 条 SQL 已是**真实测量事实**。
- `ExecutionSynchronizer.execute` 初始完整 sample，并在每条 MPD 命令确认后 sample；服务层规划前、执行后、最终确认阶段也可能额外读取。9 次完整 sample 的 0.9–1.0 秒为真实总账，但并非 9 次都能安全删除。
- 外层 `IdempotencyService` 事务包含控制及响应构造；`_stage_transport` 注册 `on_transaction_commit` 后，`database.run_transaction` 在释放锁后仍等待提交通知，`RealtimeCoordinator.publish` 再次抢共享 mutex，与后台恢复/观察形成已实测的延迟。
- 最终 fresh/CONFIRMED actual observation 可能在 HTTP 返回后由 Observer 接纳；Web `invalidate→GET /api/state` 收敛需要单独观察，而不是将后 HTTP 时间直接当成 MPD 耗时。

### Played / previous：受控映射丢失后错误全量重建

Played 业务条目不在当前 MPD 执行 Queue。`_prepare_play` 对其 add/play 后 playlist version 改变；`RecoveryJournal.accepts` 无法认可旧 binding，可能清空 `binding/synced_entries/sync_sample`。`_sync_player_queue` 于是不能复用仍有效 Pending 的业务 occurrence→MPD ID 映射，将本应保留的执行条目全部视为缺失，重新 add/play/delete；每次修改又需要完整 sample，形成极端 O(N²) 读取放大。**这是已由真实 400 add、400 delete、809 sample 和分钟级耗时证明的机制，不是歌曲格式或单次 MPD `playid` 慢。**

不能简单全局放宽 `accepts`，也不能按同 URI 重新配对重复 occurrence。修复必须证明 prepare 的最终完整 sample 与原 Pending 身份的受控交接。注意 MPD 删除旧 current 会自然触发切歌，必须保持现有“确认替代播放先于删除旧 current”的顺序语义。

主要代码：`server/app/services/playback_service.py`（`_verify_user_queue_baseline`、`_next_available_pending`、`_desired_song_uris`、`_prepare_play`、`_sync_player_queue`、`_confirm_preserved_state`）、`server/app/services/playback_execution.py`、`server/app/services/playback_recovery.py`、`server/app/player/mpd_adapter.py`、`server/app/repositories/library_repository.py`、`server/app/repositories/database.py`、`server/app/services/playback_observation.py`。

## 4. 建议的独立优化 Batch

每个 Batch 自行建有限工作分支、冻结合同、RED→GREEN、相关回归、真实环境核对、单独 acceptance；**不默认执行下一 Batch 或合并到 `v0.2`**。执行顺序可根据上一轮实测调整，但不得合并不同风险类型的工作。

### Batch 1 / P0 · Played/previous 安全映射移交

**范围**：`_prepare_play`、`_sync_player_queue`、RecoveryJournal 的准备结果/执行映射与必要执行意图、对应测试。不要顺带改 SQL、前端或全局事务。

**设计**：在同一 fixed operation owner 下，利用受控 preflight、connection epoch、partition、playlist version、完整 ID/URI/position、current、business generation 和 command receipts 证明哪些旧 Pending ID 仍属于本次执行。明确临时 prepare occurrence 到新业务 current occurrence 的唯一映射；同步只做必要的新增、移动、删除和最终绑定。任何外部修改/UNKNOWN/断线均 fail-closed。

**RED/Exit Gate**：8/400 条完整绑定队列，Played/previous 与重复 URI、外部插队、丢 ACK、重连、rollback/replay；未受影响 Pending ID 必须保留、不能再出现 400 add + 400 delete/809 sample；History/session/idempotency、绑定、权威 current 不变更错；真实 NAS 以命令数量、执行 Queue 峰值、HTTP/T6 验证。尤其检查是否产生第二次不必要的 `playid` 或进度重置。

**最低回归**：实际仓库的 `test_queue_preflight.py`、`test_d6_binding.py`、`test_d6_execution.py`、`test_d6_current.py`、`test_d6_history.py`、`test_d6_stock_joint.py`、`test_song_play_now.py`；再跑全部受影响关系测试。

### Batch 2 / P1 · 重复 Song/可用性读取减量

**范围**：Repository 的轻量级批量读取与同一事务内受控复用；`_verify_user_queue_baseline`、`_next_available_pending`、`_desired_song_uris`、`play_song_now` 需要的映射。不要更改 MPD 安全核验协议。

**设计**：按批获取最小 `song_id/file_uri/availability_status`（按真实业务合同补齐其他必要字段），避免逐项构建完整 Song；可以在同一事务/owner 内共享已验证的数据，不允许跨事务长期缓存 availability 或用旧 URI 隐藏刚发生的 Library 变更。区分当前歌曲可以保留与待播歌曲必须可用的语义。

**RED/Exit Gate**：8/400 next/song 的 `get_song` / SQL 次数上界从当前约 1200/9000 条明显下降，重复 occurrence、unavailable pending、scan 后 availability 变化、事务回滚、preflight 修复等行为不变；真实 NAS 至少 3 次可比样本比较 T1→T5/T6 中位与尾值。原 `get_song` 总约 590 ms 是待优化预算，**不能承诺全部省掉**。

### Batch 3 / P2 · 提交后通知再次争用 DB mutex

**条件**：仅在 Batch 2 后的可比实测仍证实显著提交后等待时继续。

**范围**：`_stage_transport`、`on_transaction_commit`、`RealtimeCoordinator.publish`、共享事务边界。重点核对 committed marker/sequence 是否已在 `on_transaction_visible` 取得，是否存在可避免的重复注册事务。

**RED/Exit Gate**：注入“控制事务已 commit，后台 Recovery/Observer 先取锁，提交后通知等待”的屏障，保留 WS 通知因果顺序、单次投递、失败/回放、rollback 不泄漏、`/api/state` committed cut 和重连水位一致；严禁未经证明就用裸 `create_task` 让通知失去可追踪性。若不能证明方案安全，记录不实施理由，保留旧逻辑。

### Batch 4 / P3 · 可证明有效的相邻完整样本复用

**范围**：执行器的 baseline→executor 首次 sample、final→后续 status/current 确认，必要时扩展受控 sample handoff，不改变逐命令 receipt。

**RED/Exit Gate**：精确 sample/`playlistinfo`/status 命令预算下降；注入外部 MPD 插队、跨 await 的 drift、版本改变、连接 epoch/partition 变化、当前自然跳转、torn sample、丢响应与重复 URI 时必须拒绝错误复用。不能凭 TTL、同 URI 或只查 current 来宣称完整 Queue 一致性。真实 NAS 验证长队列下一首/普通选歌。

### Batch 5 / P4 · 受控 MPD ID 直接 playid

已证实的 MPD ID 或 `addid` receipt 返回 ID 在安全 mapping 中时，评估 `ExecutionSynchronizer._send` 使用 `queue_play(id)`，代替 `play(uri)` 再全量 `playlistinfo` 搜索。保留 URI/occurrence 唯一性、重新连接后拒绝旧 ID、UNKNOWN 安全与 baseline 证明。单次通常只减少一次全队列查询（该测试环境约数十毫秒），不承诺解决 2 秒延迟。作为低风险单独补丁，而非混入 Batch 1。

### Batch 6 / P5 · HTTP 之后权威观察与 Web 收敛

先补同一浏览器 `performance.now()` 的点击、HTTP、WS invalidate、`/api/state`、DOM 更新时间；对照 Server 内部执行 ID 和诊断扰动。在确认确有重复等待后，才评估提交可见性边界接纳 MPD 已确认 final 的 actual observation，或合并已覆盖相同 epoch/sequence 的重复刷新。保留未知/过期状态如实显示、generation/freshness、rollback 后不可泄漏新 fact、迟到观察不能覆盖新状态。无浏览器时序证据时仅做分析，不臆测收益。

## 5. 每个 Batch 的统一实施流程

1. **Preflight**：实际拉取 `v0.2` 最新远端 HEAD、CI、该 Batch 的代码/测试、长期架构规格与上一 Batch acceptance；部署镜像的 OCI revision 与源码 SHA 不匹配时不能把源码推断当生产测试。
2. **合同/边界**：明确外部 MPD owner、固定 intent/receipt/epoch、duplicate occurrence、可用性、History、事务/可见性、故障/恢复与允许改动文件。先写会失败的精确测试及关系测试。
3. **TDD**：RED→实现最小修改→GREEN→相关完整回归；性能预算优先断言命令、条目、SQL 数量，不在 Fake/CI 用毫秒阈值硬判通过。不能为降测试成本删除防回归用例。
4. **实机**：单控制 owner、隔离诊断数据库/配置、只读音乐目录；安全建立分别有 8/400 条的稳定 Queue（区分 Played 历史长度、AutoPlay、相同/不同采样率）。同类安全场景尽量重复 ≥3 次，报告中位/最慢、T0–T6、MPD commands、SQL、DB/MPD 锁等待。出现 >10 秒异常先停止同类重试并只读确认实际状态；未知 Idempotency-Key terminal 不能换 key 盲重试。明确恢复 URI 不等于恢复旧 MPD ID。
5. **Exit Gate**：功能与安全关系全部通过；操作规模不再出现异常放大；真实环境延迟改善且不出现新的极端尾值；未做的真人/DAC 测试明确写 `NOT RUN`，不能冒充通过。本批独立记录验收结果与 CI；仅在新授权下实施下一批或合并。

## 6. 未覆盖：容器空闲 CPU
