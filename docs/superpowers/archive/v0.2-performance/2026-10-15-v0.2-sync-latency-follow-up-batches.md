代码确认的机制：

1. `PlaybackService._save_confirmed_status()` 调用 `PlaybackObservations.changed()`，清空实际观察；现有 `confirmed()` 维护确认身份，但不把传入状态构造成新的完整实际观察。
2. `StateObserver` 在一轮采样、Output 读取及缓存处理之后休眠 1 秒，实际周期是工作时间加休眠时间。
3. `PlaybackRecoveryRunner` 的维护路径在共享事务边界内读取 MPD。正常 AutoPlay 路径先 reconcile，再读 bound sample，之后才判断是否需要补充；稳定长队列仍有后台读取成本。
4. Observer 的外部采样已经在 DB 锁外，不能与 RecoveryRunner 的持锁采样混为一谈；两者仍共享 Adapter 通信锁。
5. 前端 mutation 返回后还会刷新状态，播放操作能力依赖权威观察。声音变化、HTTP 返回、页面恢复操作能力是不同时间点。

B4 已有验收记录中，正常 Next/song/Played 分别仍需 8/8/10 份完整样本；append 一项为 4 份。此处引用历史预算，不宣称本轮重新测试。上述机制的实际耗时占比尚未测量。

## 3. 统一安全边界

所有 Batch 必须保留：

- MPD 是实际 current、播放状态和进度的权威来源。
- occurrence 与 MPD ID 的精确映射，重复 URI 不混配。
- connection epoch、partition、playlist version、binding generation 等校验。
- fixed intent、sent/ACK/confirmed receipt，UNKNOWN 不盲重发。
- 业务 Queue、History、幂等结果的事务一致性。
- 回滚不公开成功观察，旧观察不能覆盖新操作。
- 完整用户 Queue preflight 和必要修复路径。

不通过缩短超时、降低安全校验、前端猜测成功或降低后台频率来掩盖延迟。不全局放宽 `RecoveryJournal.accepts()`，不取消共享事务锁，不把所有 MPD I/O 直接移出事务。

## 4. 步骤 0：轻量基线记录

优先复用现有诊断工具，只补缺少的浏览器时间点，不再搭建大型诊断流程。

1. 核对实际运行镜像 revision 是否对应待比较代码。
2. 分别使用约 8 首与 400 首、绑定有效的稳定队列。
3. 记录下一首、上一首、暂停、继续播放、立即播放、添加一首 Queue。
4. 每项先取 3 次，记录中位数和最大值；样本少，不称为 P95。
5. 每次记录以下四段：

| 时间段 | 用途 |
| --- | --- |
| 点击 → 请求发出 | 判断前端是否阻塞操作 |
| 请求发出 → HTTP 返回 | 判断后端处理与网络成本 |
| HTTP 返回 → 新权威观察到达 | 判断观察等待 |
| 新观察到达 → 页面状态及按钮恢复 | 判断前端收敛 |

HTTP 与 WS 可能先后交错：若合格观察先于 HTTP 返回，应记录实际事件顺序，并将“HTTP 后额外等待”记为 0，不人为要求观察晚于响应。

服务端已有数据可用时，补充共享 DB 锁等待、MPD 锁等待、完整 sample 数。浏览器使用自身单调时钟计算耗时，服务端计算自己的阶段耗时，通过请求标识关联，不直接相减两台机器的时间戳。

AutoPlay 补充、首次 UNBOUND 修复、失败重试单列，不能混进正常稳定态比较。实机动作需要另行授权并沿用单控制 owner、隔离 DB/config、只读音乐目录和恢复限制；本文件不授权建立或替换生产队列。

交付：一张前后可比较的表。无需为基线重新执行大量故障实机测试。

## 5. B6-A：操作提交后立即唤醒观察

**目标：** 以较小改动消除提交成功后等待后台下一轮的空档。

**主要范围：** `server/app/services/state_observer.py`、`server/app/services/playback_service.py` 的提交通知接入及 `server/app/main.py` 生命周期装配；具体接口在实施前冻结。

### 实施步骤

1. 为现有 Observer 增加“请求立即观察”的合并信号，继续使用原来的单一观察任务。
2. 播放控制或执行绑定发生变化后，仅在外层事务成功提交时发出信号。
3. Observer 空闲时立即采样；正在采样时记录一次后续需求。
4. 正在进行的样本若早于本次操作，不能用它消费本次刷新需求。用需求代次或等价机制避免清除信号时丢失唤醒。
5. 保留周期观察作为兜底，保持原采样验证、generation 和旧样本拒绝逻辑。
6. 多次唤醒合并，不为每次点击创建独立观察任务，不在 HTTP 回调里等待完整观察结束。

### 必要验证

- 提交成功会唤醒，回滚不会唤醒。
- 操作前开始的旧观察不能覆盖操作后状态。
- 连续请求不会生成并发采样风暴，采样结束附近的新需求不会丢失。
- 关闭服务时任务正常退出。
- 暂停、继续播放、切歌后，页面可以获得新权威观察。

### 验收

- 正常空闲情况下，提交后观察不再依赖固定 1 秒休眠结束。
- 用户操作本身的控制命令数不增加；后台额外读取单独计数，不隐藏在 mutation 预算之外。
- 短、长队列的 HTTP 后等待分别有前后记录。
- 若等待主要来自共享锁，明确转入 B7，不能把“已唤醒”写成“延迟已解决”。

## 6. B6-B：最终完整确认样本交接

**目标：** 对已有最终完整确认的路径，避免操作结束后再读一遍 MPD 才能公开实际状态。

**主要范围：** `server/app/services/playback_service.py`、`server/app/services/playback_observation.py`、现有事务可见性机制。仅在确有合同需要时修改前端收敛判断，不扩大为全局缓存系统。

### 实施步骤

1. 为每个入口标记最终可信样本所在位置：必须是全部相关 MPD 控制结束后的真实完整样本。
2. 在同一 owner 内构造待公开观察，检查最终业务 Queue、binding、current、状态与模式。不能使用 ACK 或预测状态代替真实样本。
3. 使用现有事务可见性机制，在成功提交时公开观察及对应水位；回调不执行网络 I/O。
4. 同时更新观察代次，拒绝旧后台样本回写。
5. 保留原始采样时间和 freshness；样本过旧、身份不一致或不完整时，退回 B6-A 的立即观察。
6. 暂停等只有轻量状态确认的路径先保留 B6-A，不为统一接口而扩大确认范围。
7. 核对前端收敛条件，尤其不能把原始采样时间改成提交时间，只为了满足 `observed_at >= updated_at`。必要时使用明确提交水位与控制身份判断本次操作是否被覆盖；此类合同变化须显式记录。
8. 避免有效样本已交接后，B6-A 又为同一需求无条件重复采样；只有被该样本确实覆盖的需求才能被消费，周期兜底仍保留。

### 必要验证

- 外层事务回滚，不泄漏新观察和控制 token。
- UNKNOWN、失效 binding 不进入成功路径。
- 旧样本、旧 epoch、旧 current 不覆盖新状态。
- 重复 URI 仍指向正确 occurrence。
- HTTP/WS 先后顺序改变时，前端不会倒退或永久等待。
- 采样至提交时间较长时，不能重新包装成 fresh。

### 验收

- 符合条件的操作，首个覆盖该提交且未被更新操作取代的状态快照已包含对应权威观察。
- 正常路径不为 UI 收敛额外增加完整 MPD 读取。
- 不符合条件时明确降级，不能强行确认。
- B6-A/B6-B 分别记录收益，避免重复归功。

## 7. B7：后台无变化路径缩短共享锁持有时间

**目标：** 降低 RecoveryRunner 对暂停、切歌、添加 Queue 和 `/api/state` 的阻塞。

**主要范围：** `server/app/services/playback_recovery_runner.py`、`server/app/services/playback_service.py` 的后台维护及恢复调用。第一阶段不拆用户 mutation 事务，也不改真正 adoption/refill 的控制流程。

### 实施步骤

1. 找出稳定队列、无需 adoption/refill 时，后台完整采样和占用事务锁的位置。
2. 增加后台专用检查阶段：锁内捕获不可变业务身份、Queue revision、binding 与相关代次；锁外读取真实 MPD 完整样本；回锁后重新核对捕获身份。
3. 身份发生变化则丢弃结果，不按旧计划执行控制。
4. 身份未变且确认无需维护时直接结束本轮。检查不仅包括队列长度，还包括实际 current/state、模式、错误及既有诊断和观察副作用。
5. 确实需要 adoption/refill 时进入原受保护流程，保留独立执行前校验和逐命令确认。
6. 第一阶段不复用跨窗口样本授权控制，不同时引入锁优先级调度。

### 必要验证

- 后台外部读取被阻塞时，独立本地状态读取可以完成。
- 用户在采样期间改变 Queue/current，后台旧结果被丢弃。
- 真正的自然推进接纳、AutoPlay 补充仍正确。
- 失联、取消、UNKNOWN 不触发盲重发。
- 无需维护路径的 sample 数不增加；需要维护的 fallback 额外读数单列。

### 验收

- 后台正常无变化路径不再持 DB 锁等待 MPD 网络读取。
- 400 首场景下用户操作的锁等待有实际下降证据。
- 不承诺完全消除等待：同一 MPD 连接上的通信锁仍然存在。

如仍有明显竞争，再单独评估“用户操作优先、后台有界延后”，不混入本 Batch，不取消已经发送的控制命令，也不能饿死 AutoPlay。

## 8. B5：已验证 MPD ID 直接播放

**目标：** 删除已知目标 ID 时，`play(uri)` 内部重复执行的 `playlistinfo`。

**主要范围：** `server/app/services/playback_execution.py` 的发送选择及相关映射调用。优先复用现有 `queue_play(id)`，不改公开 API。

### 实施步骤

1. 从固定 intent 的已验证映射或已确认 add receipt 获取目标 ID。
2. 使用 `queue_play(id)`，不再重新按 URI 搜索。
3. 保留执行前完整校验、执行后完整确认、重连 fencing 和 UNKNOWN 行为。

必要验证：重复 URI、目标 ID 失效、重连、丢响应、terminal replay。

验收：适用路径少一次 `playlistinfo`，播放次数不增加，目标 occurrence 不变。这是有限收益的小补丁，不作为整体延迟问题的完成标准。

## 9. B8：完整采样减负

仅在长队列仍慢且采样成本占比支持时启动。第一候选是减少完整队列响应中的非必要元数据；当前未验证目标 MPD 的精简能力或实际收益。

**主要范围：** `server/app/player/mpd_adapter.py` 的连接能力与采样响应处理，以及受影响的 Adapter 消费者。

### 实施步骤

1. 检查目标 MPD 能力与实际响应，确认哪些字段是完整身份及状态校验必需的。
2. 核对共享连接其他消费者，避免影响 Library、当前歌曲信息和 duration。
3. 如可安全精简，仅减少无关元数据，保留全部队列条目及其 ID、URI、position。
4. 连接重建后重新设置并核验能力；不支持时回退原路径。
5. 比较相同 400 首队列的响应字节量、解析时间和单份完整样本耗时。

暂不同时引入增量队列缓存、TTL 或命令组合发送。每种方案风险不同，应分别证明；组合发送也不能被当成原子快照。

验收：完整核验语义不变，长队列样本实际变便宜，短队列无明显退化。若精简会破坏其他消费者，停止此候选，不借此扩展为多连接或新缓存架构重构。
